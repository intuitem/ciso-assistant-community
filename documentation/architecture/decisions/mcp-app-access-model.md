# Serve MCP from the instance through a secretless sidecar, with OAuth consent and delegated access

- Status: Proposed (revises the first, in-process version of this decision)
- Date: 2026-11-10
- Deciders: @tchoumi313, @eric-intuitem
- Related: [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md) (the authorization model this ADR implements for MCP: delegations, planes, the profile cap and the security invariants), [service-accounts-composition](service-accounts-composition.md)

## Context

Customers want to plug AI apps (Claude Code, Copilot Studio, MCP Inspector, and others) into CISO Assistant through MCP. Until now, each user had to run the MCP server themselves: clone the repository, install Python and `uv`, and start `ca_mcp` on their own machine over stdio, with a personal access token (PAT) in its environment. Cloud apps such as Copilot Studio cannot start a local process, so someone also had to host `ca_mcp` as an HTTP server, expose it on the internet and keep it running. In both cases the app had all the user's rights through the PAT, with no consent, no expiry policy, and no way for an administrator to see or cut it.

The instance should serve MCP itself, at `<url>/mcp`, so that a user only enters a URL in their app and signs in.

MCP clients expect OAuth 2.1: they discover the server (RFC 9728, RFC 8414), register themselves (RFC 7591, DCR, or Client ID Metadata Documents), and send the user through a browser sign-in with PKCE. Most of them cannot be registered in advance, because they create a new client at each install. Copilot Studio even creates one per connection, and does not send the `resource` parameter (RFC 8707).

An MCP server handles many users' tokens and faces the network, so it is the component most likely to be compromised. The first version of this decision ran tool calls in-process in a `backend-mcp` service, which held the database credentials and the Django secret key: a compromise would have exposed everything. What a connection may do, and how the backend enforces it, is decided in [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md). This ADR decides how MCP is served and how it plugs into that model.

## Decision

We will serve MCP at `<url>/mcp` from a sidecar running `ca_mcp`, the same code as in stdio mode. The sidecar holds no secret: no database access and no backend credential. It turns MCP requests into standard API calls, carrying the caller's OAuth token, to the backend on its usual port. The backend acts as the resource server for `<url>/mcp`: it accepts an MCP token only for the operations the tools use, within the profile of its connection. allauth's IdP is the authorization server at `<url>/api`. Users connect an app themselves, on a consent page, if an administrator allowed them, and choose a profile. What the connection may then do follows [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md): **RBAC ∩ delegation ∩ profile**, with control-plane and non-delegable operations always refused. Version 1 offers levels 0 and 1, enforced by the backend; domain overrides come with that ADR's step 1a.

## Consequences

### Architecture

- **The MCP server is `ca_mcp`, run as a sidecar from the community `mcp` image.** In each customer's pod it runs next to the backend, under its own user ID, with no access to the backend's database volume, environment or secrets. It passes the caller's OAuth token through to the backend; the backend does not speak MCP.
- **An MCP token is an OAuth token that carries the `mcp` scope.** A self-registered client can be granted no scope other than `openid` and `mcp`, and the tokens of existing admin-registered apps are unchanged as long as they do not request it. Every rule of this ADR keys on this definition: the `mcp` feature flag, `can_connect_apps`, the `AppGrant`, the profile, the backstop, the inventory and the request log apply to MCP tokens, and the backend enforces them when it authenticates the token. A token from a self-registered client that does not carry the scope is refused, and so is an MCP token bound to a resource other than `<url>/mcp`.
- **The sidecar forwards only MCP tokens, and learns each one's profile from the backend with the token itself.** Before forwarding a call, it asks an inventoried backend operation for the grant behind the presented token: its user, its app and its profile. That operation answers only for MCP tokens, so the same lookup makes the sidecar refuse PATs, service-account tokens and the tokens of other OAuth apps: it never handles a credential the backstop does not bound. It caches the answer for about a minute per token. This needs no secret and no client registration for the sidecar, and `get_my_access` uses the same operation. Revocation still takes effect at once, because the backend checks the token itself on every call. `ca_mcp` keeps its PAT mode for stdio and for the standalone `mcp` service a user runs themselves; the instance's sidecar runs in OAuth mode only. It ships through the generated compose templates (`make_config.py`, which adds memcached with MCP) and the Helm chart. `docker-compose.yml` and `docker-compose-build.yml` keep the earlier read-only PAT service at `/mcp`, as a legacy exception: they ship without memcached by choice, and OAuth sign-in needs it. That service gets the same proxy rules and network isolation.
- **The backend keeps a single port** (decided by @eric-intuitem, 2026-11-09). The sidecar calls it at the address the frontend uses. The backend does not tell the sidecar's calls apart from an app calling the API directly with its MCP token: both get the same checks, the connection's profile included.
- **The backend accepts an MCP token only for the operations the tools use.** The inventory is an allowlist in the backend: the method and route of every call the `ca_mcp` tools make (over a hundred today), except those of the tools that write to the control plane (`create_folder`, `update_folder`, `update_user`), which the sidecar does not offer in OAuth mode. Each entry is a method and a route name from the backend's URL configuration, not a path pattern: `get_object` accepts ids such as `export_csv`, so a pattern like `/assets/{id}/` would also admit an action route. A test extracts these calls from the tools and fails when one is missing, so a new tool cannot ship without its entries. Each entry is reviewed when it is added, and the inventory contains no control-plane or non-delegable operation. When an inventoried operation can also write to the control plane, that part is refused to MCP tokens: creating or updating a representative with `create_user`, which creates a user account and emails an invitation, is the one known case. Every other operation refuses an MCP token, so the API reachable with an MCP token is a finite, reviewed list, whoever sends it. Recording each operation's effects, and flagging those that span several domains, waits for step 1a, when domain overrides make it matter.
- **allauth is the authorization server, with issuer `<url>/api`.** The authorize view also accepts the Knox cookie of a user already signed in to the frontend; nowhere else does the Knox cookie count as a session. The backend serves the authorization-server metadata; the sidecar serves only `/mcp` and the protected-resource metadata.
- **MCP mode requires memcached** (decided by @eric-intuitem, 2026-11-10). allauth keeps each authorization code in Django's default cache between the authorization request and the token request. Without a shared cache every backend worker has its own, and the backend runs several workers, so the token request would fail whenever it reaches another worker than the one that issued the code. The shared cache stays optional for an instance that does not use MCP. The backend refuses to turn on the `mcp` flag without it, and says why. It also refuses MCP sign-in while the cache is not shared, in case it was removed after the flag was turned on.
- **Access tokens last one hour,** set explicitly (`IDP_OIDC_ACCESS_TOKEN_EXPIRES_IN`) instead of left to allauth's default. Apps refresh their tokens at the authorization server, so the sidecar never sees a refresh token: one hour is how long a compromised sidecar could use the tokens it saw.
- **The reverse proxy isolates `/mcp`** on the app's host. On every route to the sidecar (`/mcp`, `/.well-known/oauth-protected-resource`) it removes the `Cookie` request header, removes `Set-Cookie` and `Service-Worker-Allowed` from responses, and adds `Content-Security-Policy: sandbox` and `X-Content-Type-Options: nosniff`. These rules carry weight: browsers send the frontend's session cookie to every path of the host, so without them a compromised sidecar would receive session tokens with their users' full rights. The compose files and the generated compose templates (Caddy, Traefik and BunkerWeb) apply them. The sidecar applies the same rules itself, so they hold behind any proxy. The Helm chart relies on that (decided 2026-11-12, after review: one Ingress per release): it keeps a single Ingress, since annotations apply to a whole Ingress and a second one costs a load balancer on some cloud controllers. In Kubernetes the session cookie therefore reaches the sidecar's pod and is dropped there, which protects nothing against a compromised sidecar; operators whose controller can strip it on `/mcp` alone should. The MCP administrator page (`product-docs/integrations/mcp-oauth.md`) states the rules for other proxies.
- **Removed from the first version:** the in-process `backend-mcp` service (`backend/mcp_server/`) and `Dockerfile.mcp`.

### The MCP resource boundary

The MCP specification forbids an MCP server from passing a client's token on to an API the token was not issued for, and from accepting tokens that were not issued for it. The sidecar forwards the caller's token to the backend, so the boundary of the protected resource has to be explicit:

- **One resource, two components.** The protected resource `<url>/mcp` is implemented by two components deployed together: the protocol front, which is the sidecar, and the execution endpoint, which is the backend serving the inventoried operations to MCP tokens. It is the same resource that the first version of this decision ran in a single process. Moving execution out of the network-facing process keeps secrets out of it without creating a new resource.
- **The execution endpoint is the resource server.** The backend validates every MCP token itself, without relying on the front's check: active, issued by this instance, carrying the `mcp` scope, bound to no other resource, and backed by a live `AppGrant`. Only then does it run an operation from the inventory.
- **The `mcp` scope ties a token to this resource.** The scope means "may use MCP" and is honored nowhere else: the backend treats every token that carries it as an MCP token, restricted to the inventoried operations. A client that sends a resource indicator (RFC 8707) must name `<url>/mcp`: a grant that requests the `mcp` scope with any other resource is refused, and so is a token bound to another resource. A client that omits it, as Copilot Studio does, is held to the same rules through the scope. We key on the scope, and not on a recorded audience, for two reasons. allauth carries the scope on every path, but does not record the resource on silent sign-in. And allauth's own resource check compares a token's resource with the URL of each request, so it would refuse a token bound to `<url>/mcp` on the backend's routes: for MCP tokens, the backend applies the rule above in its place.
- **The backend is not a downstream resource for MCP tokens.** An MCP token reaches only the inventoried operations of the MCP resource; every other operation refuses it. The front presents the token to nothing else; its grant lookup is one of the inventoried operations.
- **The reasons behind the specification's rule are covered.** The backend's controls cannot be bypassed, because it applies them to every call that carries an MCP token, whoever sends it. Every action is attributed to the app (`via_app`). The backend does not rely on the front's validation, the connection's profile included.
- **Accepted interpretation.** The MCP specification does not say explicitly whether an MCP server may be split into a protocol front and an execution endpoint that serve one resource. Clients and the authorization server see a single resource at `<url>/mcp`. The execution endpoint shares the backend's port with the API, but an MCP token reaches only the MCP resource's operations there. We accept the reading above (decided by @eric-intuitem, 2026-11-08).
- **Fallback.** If a later revision of the specification rules this out, the front exchanges the MCP token for an internal credential (token exchange, RFC 8693). allauth does not implement token exchange, so this would mean a custom grant, a client secret in the front, and a second token carrying the same delegation.

### Who may connect

- **Clients register through DCR.** Self-registered clients get nothing until a user who may connect apps approves them on the consent page.
- **A connection that is not used for 30 days ends:** its refresh token expires and the user must approve the app again (`OAUTH_REFRESH_TOKEN_IDLE_DAYS`, `0` = never). allauth issues a new refresh token at each refresh, so an app in use never notices.
- **The `mcp` feature flag turns MCP on or off for the instance.** Off: every MCP connection is blocked, but kept, and works again when it is turned back on. The backend checks it when it authenticates an MCP token, so calls that skip the sidecar are blocked too. It does not affect other OAuth apps, nor `ca_mcp` run by a user over stdio with their own PAT.
- **`can_connect_apps` on the user** is off by default and only an administrator can change it. It applies to MCP tokens only: the tokens of existing admin-registered apps keep working without it, since the migration sets it to false for every existing user. Unticking it revokes all the user's MCP connections at once; deactivating the user revokes every token.
- **Administrators see every connection** in **Organization > Connected apps**, with its redirect hosts and current profile, and can search by user or app. They can revoke one, or revoke an app for everyone. Revoking an app for everyone cuts the selected registration for all its users, and deletes it when it is self-registered so its ID cannot be reused. It does not extend to other registrations that share its name and return address: a self-registered app chooses its own name, so two registrations that look alike are not proven to be the same app (decided 2026-11-12, after review). Copilot Studio registers again for each connection, so cutting all its connections at once takes a batch revocation, left for later.

### What an app may do

- **In v1, the user chooses on the consent page what the app may do: Read, always, plus any of Create, Update and Delete** (decided by @eric-intuitem, 2026-11-10; Delete was first folded into Update). Each combination is a built-in profile that cannot be changed, eight in all, and Read only is preselected. The consent page may group the choices, but every combination stays available. A client that skips consent gets Read only. The profile with all four operations is level 0 and the others are level 1. Step 1a brings the presets of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md) and domain overrides (level 2), edited afterwards on the connection.
- **The choice is stored as a grant per user and client (`AppGrant`), not on the token,** because allauth issues new tokens at each refresh and copies nothing across. In v1 the grant points to the chosen profile; since built-in profiles cannot change, the profile cap has nothing to do yet. The grant also has a `folder_overrides` field, keyed by folder ID, that stays empty and unread in v1, so that domain overrides need no new data model. From step 1a the grant stores the consented selection, capped by the connection's profile. No grant means no access; there is no fallback.
- **The backend enforces the connection's profile in the central access functions, from the permission each check asks for** (decided at the team review of 2026-11-10; the profile first rested on the sidecar alone, then on the HTTP method). The backend loads the grant when it authenticates an MCP token and keeps it in the credential context of the request. `RoleAssignment.is_access_allowed`, `_get_grant_folder_set` (behind `get_allowed_folder_ids` and `get_accessible_object_ids`) and `has_permission_anywhere` map the permission codename to its operation: `view_` to read, `add_` to create, `change_` to update and `delete_` to delete. They refuse it unless the profile allows that operation, refuse every write to a control-plane model, every permission on credentials and on models that hold secrets, and every custom permission that is not mapped to an operation, then let RBAC decide as usual. Two custom permissions are mapped, both to read: the auditor view of an audit (`view_compliance_assessment_full`) and the published-only view of documents (`view_published_documentcontainer`). Every other one is refused, whatever its name: the `approve_` and `transition_` permissions, the full view of users (`view_user_full`, their sign-in and administration details) and the audit log permissions. What a request may do is thus RBAC ∩ profile, in every view and whatever its HTTP method: a `POST` that only reads, such as a search, needs read, and an action route needs the permissions its view checks. We chose this over the HTTP method because the method does not always say what a route does, and the central functions are where step 1a adds domain overrides anyway. Some action routes check a permission that does not say what they do: `sync_from_ebios_rm` and `retrigger-all-simulations` are `POST` actions that check `add_` but update. The inventory marks each operation's effect, and the backend also refuses an MCP token whose profile does not allow that effect. These two actions therefore need both create and update: create for the view's check, update for the inventory's. The profile binds the token, whoever presents it: an app that calls the API directly, or a compromised sidecar, gets no more than the user consented to.
- **Write profiles are off until an administrator allows them.** A second feature flag, `mcp_write`, is off by default and requires `mcp`. While it is off, the consent page offers Read only alone, and the backend treats every MCP token as Read only, whatever its profile. Connections keep their profile and use it again when the flag is turned on. It is the organization's lever against prompt injection (see Remaining risks).
- **Each tool's class is declared next to the tool,** in `CREATE_TOOLS`, `UPDATE_TOOLS` and `DELETE_TOOLS` in `ca_mcp`, never guessed from its name; every other tool is a read. The two delete tools (`delete_vulnerability`, `delete_task_template`) move from `UPDATE_TOOLS` to `DELETE_TOOLS`. The sidecar uses the classes to hide the tools a profile does not allow, and to refuse them with a clear message; it refuses unknown tools. A test fails when a tool's calls are refused by the backend to a profile that holds the tool's class, so the sidecar and the backend cannot disagree. No route that writes while checking only a `view_` permission may enter the inventory: the review of each entry checks it, and no tool calls one today (`loaded-libraries/{id}/update/` writes, and is not listed).
- **The backend backstop applies from v1, through the inventory.** The inventory lists no control-plane or non-delegable operation, so the backend refuses them to MCP tokens like any other unlisted operation. `IsGlobalAdmin` also refuses MCP tokens, from the request's credential. Every MCP token is thus at most a level-0 delegation, and the routes of the tools that write to the control plane are refused even to an app that skips the sidecar. The credential context and the central check of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md) apply to MCP tokens from v1, so control-plane writes are refused there too; step 1a adds domain overrides and the registry that replaces the inventory.
- **`tools/list` hides the tools the profile does not allow,** and the `get_my_access` tool tells the agent what it can and cannot do. We do not use step-up (`insufficient_scope`) for now.
- **MCP has a single scope, `mcp`,** which means "may use MCP" and defines an MCP token. It was named `mcp:read` during development and is renamed before the first release, since it does not mean read-only. What the app may do comes only from its profile, and from step 1a its delegation.
- **Existing admin-registered OAuth clients keep today's behavior,** unfiltered, as long as they do not request the `mcp` scope.

### Audit and limits

- **Audit entries for changes made through an app keep the user as the actor and add `via_app`** (client ID, name, profile). SIEM events carry it as `actor.app_name` and `actor.app_uid` in OCSF, and as `via_app` in the raw format. The backend records the app when it authenticates an MCP token, and clears it when each request begins, so a later request on the same worker is never attributed to the app.
- **The backend's request log names the app on every request made with an MCP token.** The backend already logs every request with its user, method, path and status; authenticating an MCP token adds the app's client ID. This is the security record: reads stay traceable when a call skips the sidecar or the sidecar is compromised.
- **The sidecar logs every tool call** as `mcp tool call`, with the user, app, profile, tool, outcome, duration and answer size. This log is for operations, such as tuning budgets, not a security record.
- **Each connection (one user with one app) has a budget,** enforced by the sidecar: 60 calls per minute (`MCP_MAX_CALLS_PER_MINUTE`) and 2,000,000 characters per hour (`MCP_MAX_RESPONSE_CHARS_PER_HOUR`); `0` turns a limit off. The budget stops a looping or prompt-injected agent from overloading the instance. It is a safeguard for well-behaved deployments, not a security boundary: a compromised sidecar would ignore it.
- **The sidecar limits how many backend calls it runs at once,** two by default. MCP calls share the backend's workers with the interface, three by default, and must not occupy them all.

### Next and later

- **PKCE required for confidential clients too.**
- **Client ID Metadata Documents,** the registration the MCP specification prefers. It stays off in v1: it makes the backend fetch a URL the client chooses, which needs its own review.
- **Apps as a governance list.** An administrator registers an app with its own client ID. Server apps (confidential clients with an HTTPS redirect) can be marked Trusted; desktop apps (loopback redirect) can only be Allowed, never Trusted, because any program on the machine can listen on localhost and pretend to be them (RFC 8252, section 8.6). Skip consent is allowed only for trusted server apps. A deny list on redirect hosts blocks self-registration from those hosts and revokes their connections. Self-registered clients that were never used, or not used for a long time, are cleaned up. Consent policies per app follow step 2 of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md).
- **Making `resource` required,** once Copilot Studio sends it.
- **A per-user budget** on top of the per-connection one, so that many apps cannot add up.
- **Workflow tools** (risk acceptance, commitment, assignment): their custom permissions are mapped in the registry of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md), or kept non-delegable.

## Security

**Conclusion: serving MCP this way never gives an app more than its user consented to, within that user's data-plane rights on the inventoried operations, and a compromise of the network-facing component stays bounded.** The sidecar holds no secrets that open the database or the instance; the backend makes every authorization decision, the connection's profile included, under the invariants of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md).

### Why the sidecar cannot be turned into more access

1. **It holds nothing worth stealing beyond the tokens it sees.** No database access, no Django secret key, no IdP signing key, no client secret. The tokens it sees are MCP tokens: it refuses every other credential from the first release, so no client is configured to send it a PAT.
2. **MCP tokens are only valid at the MCP resource.** The backend recognizes an MCP token by its `mcp` scope, refuses one bound to another resource, and accepts it only on the inventoried operations. The token is never accepted by an API it was not issued for. An app that skips the MCP server reaches the same operations, under the same profile and the same backstop.
3. **A compromised sidecar stays bounded.** The backstop refuses control-plane operations, administrator endpoints and non-delegable actions to MCP tokens, on operations that are all inventoried, and the backend holds each token to its connection's profile. A compromise gives what those profiles allow, for the users whose tokens pass through it, until those tokens expire, one hour at most: it cannot create users, change emails, mint PATs or alter settings. Revoking a connection takes effect at once.
4. **Session cookies are kept from the sidecar, and its responses cannot act as the app.** Its responses cannot run script as the app or set cookies on the app's host: the sidecar sets these rules itself, and the proxy too where we ship one. In the compose deployments the proxy removes the cookies on the MCP routes, so they never reach the sidecar. With the Helm chart they reach the sidecar's pod and the sidecar drops them, which does not hold against a compromised sidecar (see Remaining risks).
5. **Consent stays with users who may connect apps.** DCR is open, but a registered client gets nothing until such a user approves it. The consent page shows each app's redirect hosts, the only reliable sign of who it is, since a self-registered app chooses its own name. Loopback redirects cannot prove which program is listening, so desktop apps are never trusted.
6. **Every change is attributed, every request traced.** Audit entries carry `via_app`, and the backend's request log names the app on every request made with an MCP token, whether or not it went through the sidecar, so an incident can be traced to one connection and revoked there.

### Verification

Tests provide evidence, not proof; they are required validation for this design:

- every tool's calls allowed to a profile that holds its declared class, and no route that writes behind a `view_` check in the inventory (`GET /api/loaded-libraries/{id}/update/` writes);
- the profile enforced by the central functions on calls that skip the sidecar: `add_`, `change_` and `delete_` checks refused to a Read only connection, each allowed only by a profile that includes its operation, custom permissions such as `approve_` refused to every profile, and writes to control-plane models refused even to a user who holds them;
- every `add_`, `change_` and `delete_` check refused to MCP tokens while `mcp_write` is off;
- every call the offered tools make found in the inventory, and the control-plane tools not offered in OAuth mode;
- every inventoried operation called with an MCP token; MCP tokens refused on every operation outside the inventory, including the routes of the control-plane tools and an action route reached through an object id; a self-registered client's token without the `mcp` scope refused; an MCP token bound to another resource refused, and a grant requesting the `mcp` scope with another resource refused;
- the `mcp` flag refused without a shared cache, and MCP sign-in refused once the cache is no longer shared (a sign-in split across two workers is checked by hand: unit tests run in one process);
- `create_user` refused to MCP tokens when creating or updating a representative;
- the `mcp` flag and `can_connect_apps` enforced on MCP tokens, including calls that skip the sidecar, and not on the tokens of admin-registered apps that do not request the `mcp` scope;
- the grant lookup answering only for MCP tokens, and the sidecar refusing PATs, service-account tokens and other OAuth tokens;
- the app recorded in the backend's request log for every request made with an MCP token, and `via_app` absent from a request that follows an MCP request on the same worker;
- no control-plane or non-delegable operation in the inventory;
- the sidecar applying the isolation rules itself; each proxy configuration we ship applying them too is checked by hand against a running deployment (Caddy, Traefik and BunkerWeb), not by a test.

### Remaining risks, accepted as low

- **Indirect prompt injection.** Agents read text written by less trusted parties, such as third-party respondents, imported files and data synchronized from other tools, and that text can carry instructions. An agent that holds write tools could then change data with its user's rights, and any agent could be led to send what it reads elsewhere through the AI app, which we do not control. Write profiles are off until an administrator allows them, Read only is preselected, the control plane is out of reach, and every change is attributed to the app. What an AI app does with the data it reads remains the responsibility of that app and of the user who connects it.
- **The profile follows the permissions each view checks.** A view that writes after checking only a `view_` permission, or none, escapes the split between create, update and delete, as it already escapes RBAC. A test checks every tool's calls against its class, and the review of each inventory entry looks for such writes. Review alone catches a route that starts writing this way in a later release, or one whose only side effect is an email or an outbound call; none is known.
- **Our reading of the MCP specification.** Forwarding the token rests on the resource boundary above, and on recognizing MCP tokens by their scope where a client sent no resource indicator. A reviewer, or a future revision of the specification, could read the rule more strictly; token exchange remains the fallback.
- **A self-registered app can trick a user into consenting.** It then gets what that user consented to, within their data-plane rights on the inventoried operations, and never the control plane. Setting `OAUTH_DCR_ALLOWED_REDIRECT_HOSTS` to the AI clients an instance supports limits which apps can register at all.
- **A deployment without the proxy rules for `/mcp`.** Browsers then send session cookies to the sidecar. Its responses still cannot run on the app's origin, since the sidecar sets the sandbox headers itself, and it drops the cookies; but a compromised sidecar would receive them, with their users' full rights. Every compose file and template we ship applies the rules in the proxy. The Helm chart does not, by decision, and the MCP administrator page asks operators whose ingress controller can strip the cookie on `/mcp` alone to do so.
- **In Kubernetes, the sidecar shares the backend pod's network.** In the compose deployments it runs on its own network with the backend and the proxy only, so it cannot reach the database, memcached or Qdrant. In a pod, containers share one network namespace and no network policy can tell them apart: a compromised sidecar can reach what the backend reaches. Postgres needs credentials the sidecar does not hold; Qdrant has no authentication, so the content indexed for chat is exposed to it. Protecting Qdrant with an API key closes this, and is a separate change.
- **v1's classification is the hand-reviewed inventory.** Keeping control-plane operations out of it rests on reviewing each route, including what a listed data-plane operation may write as a side effect, such as the user account a representative's `create_user` creates. Step 1a adds the registry and its fail-closed test for the whole API.

### What would change this assessment

Giving the sidecar database access or a backend secret, letting it forward credentials other than MCP tokens, accepting MCP tokens on operations outside the inventory or bound to another resource, presenting them to any other resource, enforcing the profile anywhere but in the backend, removing the backstop, or dropping the proxy isolation rules from another deployment file we ship (the Helm chart already relies on the sidecar's own rules, by the decision above) would reopen these questions and requires a new decision.
