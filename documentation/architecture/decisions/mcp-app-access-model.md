# Serve MCP from the instance through a secretless sidecar, with OAuth consent and delegated access

- Status: Proposed (revises the first, in-process version of this decision)
- Date: 2026-11-09
- Deciders: @tchoumi313, @eric-intuitem
- Related: [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md) (the authorization model this ADR implements for MCP: delegations, planes, the profile cap and the security invariants), [service-accounts-composition](service-accounts-composition.md)

## Context

Customers want to plug AI apps (Claude Code, Copilot Studio, MCP Inspector, and others) into CISO Assistant through MCP. Until now, each user had to run the MCP server themselves: clone the repository, install Python and `uv`, and start `ca_mcp` on their own machine over stdio, with a personal access token (PAT) in its environment. Cloud apps such as Copilot Studio cannot start a local process, so someone also had to host `ca_mcp` as an HTTP server, expose it on the internet and keep it running. In both cases the app had all the user's rights through the PAT, with no consent, no expiry policy, and no way for an administrator to see or cut it.

The instance should serve MCP itself, at `<url>/mcp`, so that a user only enters a URL in their app and signs in.

MCP clients expect OAuth 2.1: they discover the server (RFC 9728, RFC 8414), register themselves (RFC 7591, DCR, or Client ID Metadata Documents), and send the user through a browser sign-in with PKCE. Most of them cannot be registered in advance, because they create a new client at each install. Copilot Studio even creates one per connection, and does not send the `resource` parameter (RFC 8707).

An MCP server handles many users' tokens and faces the network, so it is the component most likely to be compromised. The first version of this decision ran tool calls in-process in a `backend-mcp` service, which held the database credentials and the Django secret key: a compromise would have exposed everything. What a connection may do, and how the backend enforces it, is decided in [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md). This ADR decides how MCP is served and how it plugs into that model.

## Decision

We will serve MCP at `<url>/mcp` from a sidecar running `ca_mcp`, the same code as in stdio mode. The sidecar holds no secret: no database access and no backend credential. It turns MCP requests into standard API calls, carrying the caller's OAuth token, to the backend on its usual port. The backend acts as the resource server for `<url>/mcp`: it accepts an MCP token only for the operations the tools use. allauth's IdP is the authorization server at `<url>/api`. Users connect an app themselves, on a consent page, if an administrator allowed them, and choose a profile. What the connection may then do follows [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md): **RBAC ∩ delegation ∩ profile**, with control-plane and non-delegable operations always refused. Version 1 offers levels 0 and 1, enforced by the MCP server, with a backend backstop; domain overrides come with that ADR's step 1a.

## Consequences

### Architecture

- **The MCP server is `ca_mcp`, run as a sidecar from the community `mcp` image.** In each customer's pod it runs next to the backend, under its own user ID, with no access to the backend's database volume, environment or secrets. It passes the caller's OAuth token through to the backend; the backend does not speak MCP.
- **An MCP token is an OAuth token whose audience includes `<url>/mcp`.** The authorization server adds that audience to every grant that requests the `mcp` scope, and only to those, so the tokens of existing admin-registered apps are unchanged. Every rule of this ADR keys on this definition: the `mcp` feature flag, `can_connect_apps`, the `AppGrant`, the backstop, the inventory and the request log apply to MCP tokens, and the backend enforces them when it authenticates the token. A token from a self-registered client that is not an MCP token is refused.
- **The sidecar forwards only MCP tokens, and learns each one's profile from the backend with the token itself.** Before forwarding a call, it asks an inventoried backend operation for the grant behind the presented token: its user, its app and its profile. That operation answers only for MCP tokens, so the same lookup makes the sidecar refuse PATs, service-account tokens and the tokens of other OAuth apps: it never handles a credential the backstop does not bound. It caches the answer for about a minute per token. This needs no secret and no client registration for the sidecar, and `get_my_access` uses the same operation. Revocation still takes effect at once, because the backend checks the token itself on every call. `ca_mcp` keeps its PAT mode for stdio and for the standalone `mcp` service a user runs themselves; the instance's sidecar runs in OAuth mode only.
- **The backend keeps a single port** (decided by @eric-intuitem, 2026-11-09). The sidecar calls it at the address the frontend uses. The backend does not tell the sidecar's calls apart from an app calling the API directly with its MCP token: both get the same checks. In v1, the connection's profile is enforced only for calls that go through the sidecar (see Remaining risks).
- **The backend accepts an MCP token only for the operations the tools use.** The inventory is an allowlist in the backend: the method and route of every call the `ca_mcp` tools make (over a hundred today), except those of the tools that write to the control plane (`create_folder`, `update_folder`, `update_user`), which the sidecar does not offer in OAuth mode. A test extracts these calls from the tools and fails when one is missing, so a new tool cannot ship without its entries. Each entry is reviewed when it is added, and the inventory contains no control-plane or non-delegable operation. When an inventoried operation can also write to the control plane, that part is refused to MCP tokens: creating or updating a representative with `create_user`, which creates a user account and emails an invitation, is the one known case. Every other operation refuses an MCP token, so the API reachable with an MCP token is a finite, reviewed list, whoever sends it. Recording each operation's effects, and flagging those that span several domains, waits for step 1a, when domain overrides make it matter.
- **allauth is the authorization server, with issuer `<url>/api`.** The authorize view also accepts the Knox cookie of a user already signed in to the frontend; nowhere else does the Knox cookie count as a session. The backend serves the authorization-server metadata; the sidecar serves only `/mcp` and the protected-resource metadata.
- **The reverse proxy isolates `/mcp`** on the app's host. On every route to the sidecar (`/mcp`, `/.well-known/oauth-protected-resource`) it removes the `Cookie` request header, removes `Set-Cookie` and `Service-Worker-Allowed` from responses, and adds `Content-Security-Policy: sandbox` and `X-Content-Type-Options: nosniff`. The compose Caddy configuration does this by default, and the MCP administrator page (`product-docs/integrations/mcp-oauth.md`) states the rules for other proxies.
- **Removed from the first version:** the in-process `backend-mcp` service (`backend/mcp_server/`) and `Dockerfile.mcp`.

### The MCP resource boundary

The MCP specification forbids an MCP server from passing a client's token on to an API the token was not issued for, and from accepting tokens that were not issued for it. The sidecar forwards the caller's token to the backend, so the boundary of the protected resource has to be explicit:

- **One resource, two components.** The protected resource `<url>/mcp` is implemented by two components deployed together: the protocol front, which is the sidecar, and the execution endpoint, which is the backend serving the inventoried operations to MCP tokens. It is the same resource that the first version of this decision ran in a single process. Moving execution out of the network-facing process keeps secrets out of it without creating a new resource.
- **The execution endpoint is the resource server.** The backend validates every MCP token itself, without relying on the front's check: active, issued by this instance, audience `<url>/mcp`, and a live `AppGrant`. Only then does it run an operation from the inventory.
- **Every MCP token carries that audience.** Clients send it as a resource indicator (RFC 8707). When a client omits it, as Copilot Studio does, the authorization server records `<url>/mcp` on the grant itself, so the audience check is the same for every client. allauth carries a grant's resource from the authorization request to the code and then to the token, and keeps it across refreshes, so the authorize view can set it. A grant that requests the `mcp` scope with any other resource is refused.
- **The backend is not a downstream resource for MCP tokens.** An MCP token reaches only the inventoried operations of the MCP resource; every other operation refuses it. The front presents the token to nothing else; its grant lookup is one of the inventoried operations.
- **The reasons behind the specification's rule are covered.** The backend's controls cannot be bypassed, because it applies them to every call that carries an MCP token, whoever sends it. Every action is attributed to the app (`via_app`). The backend does not rely on the front's validation. In v1 the connection's profile is the one control the front applies alone; step 1a moves it to the backend.
- **Accepted interpretation.** The MCP specification does not say explicitly whether an MCP server may be split into a protocol front and an execution endpoint that share one audience. Clients and the authorization server see a single resource at `<url>/mcp`. The execution endpoint shares the backend's port with the API, but an MCP token reaches only the MCP resource's operations there. We accept the reading above (decided by @eric-intuitem, 2026-11-08).
- **Fallback.** If a later revision of the specification rules this out, the front exchanges the MCP token for an internal credential (token exchange, RFC 8693). allauth does not implement token exchange, so this would mean a custom grant, a client secret in the front, and a second token carrying the same delegation.

### Who may connect

- **Clients register through DCR,** and through Client ID Metadata Documents where they support it. Self-registered clients get nothing until a user who may connect apps approves them on the consent page.
- **A connection that is not used for 30 days ends:** its refresh token expires and the user must approve the app again (`OAUTH_REFRESH_TOKEN_IDLE_DAYS`, `0` = never). allauth issues a new refresh token at each refresh, so an app in use never notices.
- **The `mcp` feature flag turns MCP on or off for the instance.** Off: every MCP connection is blocked, but kept, and works again when it is turned back on. The backend checks it when it authenticates an MCP token, so calls that skip the sidecar are blocked too. It does not affect other OAuth apps, nor `ca_mcp` run by a user over stdio with their own PAT.
- **`can_connect_apps` on the user** is off by default and only an administrator can change it. It applies to MCP tokens only: the tokens of existing admin-registered apps keep working without it, since the migration sets it to false for every existing user. Unticking it revokes all the user's MCP connections at once; deactivating the user revokes every token.
- **Administrators see every connection** in **Organization > Connected apps**, with its redirect hosts and current profile, and can search by user or app. They can revoke one, or revoke an app for everyone. Revoking an app for everyone groups the registrations that share a name and a return address, and deletes self-registered clients so their IDs cannot be reused.

### What an app may do

- **In v1, the user picks one of four built-in profiles on the consent page:** Read only (preselected), Read and create, Read and update, or Read, create and update. Update includes deleting, and the profiles cannot be changed. A client that skips consent gets Read only. "Read, create and update" is level 0 and the other three are level 1. Step 1a brings the presets of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md), with a separate Delete, and domain overrides (level 2), edited afterwards on the connection.
- **The choice is stored as a grant per user and client (`AppGrant`), not on the token,** because allauth issues new tokens at each refresh and copies nothing across. In v1 the grant points to the chosen profile; since built-in profiles cannot change, the profile cap has nothing to do yet. From step 1a the grant stores the consented selection, capped by the connection's profile. No grant means no access; there is no fallback.
- **Each tool's class is declared next to the tool,** in `CREATE_TOOLS` and `UPDATE_TOOLS` in `ca_mcp`, never guessed from its name; every other tool is a read. A test fails when a read tool calls a write method (`POST`, `PUT`, `PATCH`, `DELETE`) or a `GET` route that writes. The review of each `GET` entry checks whether it writes, and the inventory marks those that do, such as `loaded-libraries/{id}/update/`.
- **In v1, the sidecar enforces the connection's profile,** which we trust because we maintain its code. A tool is allowed when the profile allows its class; unknown tools are refused. The sidecar cannot know which domain a call will touch, so v1 offers levels 0 and 1 only.
- **The backend backstop applies from v1, through the inventory.** The inventory lists no control-plane or non-delegable operation, so the backend refuses them to MCP tokens like any other unlisted operation. `IsGlobalAdmin` also refuses MCP tokens, from the request's credential. Every MCP token is thus a level-0 delegation, and the routes of the tools that write to the control plane are refused even to an app that skips the sidecar. The credential context and the central check of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md) arrive with step 1a, where the backend applies the grant's own delegation.
- **`tools/list` hides the tools the profile does not allow,** and the `get_my_access` tool tells the agent what it can and cannot do. We do not use step-up (`insufficient_scope`) for now.
- **MCP has a single scope, `mcp`,** which means "may use MCP". It was named `mcp:read` during development and is renamed before the first release, since it does not mean read-only. Every MCP token gets it. What the app may do comes only from its profile, and from step 1a its delegation.
- **Existing admin-registered OAuth clients keep today's behavior,** unfiltered, as long as they do not request the `mcp` scope.

### Audit and limits

- **Audit entries for changes made through an app keep the user as the actor and add `via_app`** (client ID, name, profile). SIEM events carry it as `actor.app_name` and `actor.app_uid` in OCSF, and as `via_app` in the raw format.
- **The backend's request log names the app on every request made with an MCP token.** The backend already logs every request with its user, method, path and status; authenticating an MCP token adds the app's client ID. This is the security record: reads stay traceable when a call skips the sidecar or the sidecar is compromised.
- **The sidecar logs every tool call** as `mcp tool call`, with the user, app, profile, tool, outcome, duration and answer size. This log is for operations, such as tuning budgets, not a security record.
- **Each connection (one user with one app) has a budget,** enforced by the sidecar: 60 calls per minute (`MCP_MAX_CALLS_PER_MINUTE`) and 2,000,000 characters per hour (`MCP_MAX_RESPONSE_CHARS_PER_HOUR`); `0` turns a limit off. The budget stops a looping or prompt-injected agent from overloading the instance. It is a safeguard for well-behaved deployments, not a security boundary: a compromised sidecar would ignore it.

### Next and later

- **PKCE required for confidential clients too.**
- **Apps as a governance list.** An administrator registers an app with its own client ID. Server apps (confidential clients with an HTTPS redirect) can be marked Trusted; desktop apps (loopback redirect) can only be Allowed, never Trusted, because any program on the machine can listen on localhost and pretend to be them (RFC 8252, section 8.6). Skip consent is allowed only for trusted server apps. A deny list on redirect hosts blocks self-registration from those hosts and revokes their connections. Self-registered clients that were never used, or not used for a long time, are cleaned up. Consent policies per app follow step 2 of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md).
- **Making `resource` required,** once Copilot Studio sends it.
- **A per-user budget** on top of the per-connection one, so that many apps cannot add up.
- **Workflow tools** (risk acceptance, commitment, assignment): their custom permissions are mapped in the registry of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md), or kept non-delegable.

## Security

**Conclusion: serving MCP this way never gives an app more than its user's data-plane rights on the inventoried operations, and a compromise of the network-facing component stays bounded.** The sidecar holds no secrets that open the database or the instance; the backend makes every authorization decision except, in v1, the connection's profile, under the invariants of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md). Step 1a moves that last decision to the backend.

### Why the sidecar cannot be turned into more access

1. **It holds nothing worth stealing beyond the tokens it sees.** No database access, no Django secret key, no IdP signing key, no client secret. The tokens it sees are MCP tokens: it refuses every other credential from the first release, so no client is configured to send it a PAT.
2. **MCP tokens are only valid at the MCP resource.** The backend validates each token's audience itself, every MCP token carries `<url>/mcp` as its audience, and only the inventoried operations accept such tokens. The token is never accepted by an API it was not issued for. An app that skips the MCP server reaches the same operations, under the same backstop.
3. **A compromised sidecar stays bounded.** The backstop refuses control-plane operations, administrator endpoints and non-delegable actions to MCP tokens, on operations that are all inventoried. A compromise gives the data-plane rights of the users whose tokens pass through it, until those tokens expire: it cannot create users, change emails, mint PATs or alter settings. Revoking a connection takes effect at once.
4. **Browsers never hand session cookies to the sidecar.** The reverse proxy removes them on the MCP routes, and its responses cannot run script as the app or set cookies on the app's host.
5. **Consent stays with users who may connect apps.** DCR is open, but a registered client gets nothing until such a user approves it. The consent page shows each app's redirect hosts, the only reliable sign of who it is, since a self-registered app chooses its own name. Loopback redirects cannot prove which program is listening, so desktop apps are never trusted.
6. **Every change is attributed, every request traced.** Audit entries carry `via_app`, and the backend's request log names the app on every request made with an MCP token, whether or not it went through the sidecar, so an incident can be traced to one connection and revoked there.

### Verification

Tests provide evidence, not proof; they are required validation for this design:

- no read tool calling a write method, or a `GET` route the inventory marks as writing (`GET /api/loaded-libraries/{id}/update/` writes);
- every call the offered tools make found in the inventory, and the control-plane tools not offered in OAuth mode;
- every inventoried operation called with an MCP token; MCP tokens refused on every operation outside the inventory, including the routes of the control-plane tools; a self-registered client's token without the MCP audience refused; a grant requesting the `mcp` scope with another resource refused;
- `create_user` refused to MCP tokens when creating or updating a representative;
- the `mcp` flag and `can_connect_apps` enforced on MCP tokens, including calls that skip the sidecar, and not on the tokens of admin-registered apps that do not request the `mcp` scope;
- the grant lookup answering only for MCP tokens, and the sidecar refusing PATs, service-account tokens and other OAuth tokens;
- the app recorded in the backend's request log for every request made with an MCP token;
- no control-plane or non-delegable operation in the inventory;
- the compose proxy configuration applying the isolation rules.

### Remaining risks, accepted as low

- **In v1, the connection's profile rests on the sidecar** (accepted by @eric-intuitem, 2026-11-09). Two paths escape it: a compromised sidecar, and an app that presents its MCP token to the backend directly. Either gets the full data-plane rights of the user on the inventoried operations, whatever the profile, and never the control plane. A compromised sidecar keeps this until the tokens it saw expire, so a shorter access-token lifetime reduces that window. An app calling directly keeps it until its connection is revoked. A misclassified tool could also escape the profile: the tests catch a read tool that calls a write method or a `GET` route marked as writing. Review alone catches a `GET` route that starts writing in a later release, or one whose only side effect is an email or an outbound call; none is known. Step 1a of [delegated-permissions-over-rbac](delegated-permissions-over-rbac.md) moves enforcement to the backend and closes both paths.
- **The direct path depends on routing, and each administrator owns that choice.** It exists only where apps can reach `/api`: the compose and Helm configurations route it publicly, as does any deployment that offers API access. A deployment that exposes `/mcp` and the OAuth endpoints, and no other part of `/api`, does not have it. The MCP administrator page states the trade-off: in v1, consent choices bind only calls made through `/mcp`, and exposing `/api` lets a connected app act with its user's full data-plane rights. Well-known AI clients call only the MCP server, and `OAUTH_DCR_ALLOWED_REDIRECT_HOSTS` limits which apps can register.
- **Our reading of the MCP specification.** Forwarding the token rests on the resource boundary above. A reviewer, or a future revision of the specification, could read the rule more strictly; token exchange remains the fallback.
- **A self-registered app can trick a user into consenting.** It then gets that user's data-plane rights on the inventoried operations, and never the control plane. In v1 it can ignore the consented profile by calling the backend directly (see above); from step 1a it gets only what was consented. Setting `OAUTH_DCR_ALLOWED_REDIRECT_HOSTS` to the AI clients an instance supports limits which apps can register at all.
- **A deployment without the proxy rules for `/mcp`.** Browsers could then send session cookies to the sidecar, and its responses would run on the app's origin. The compose configuration applies the rules by default, and the MCP administrator page states them for other proxies.
- **v1's classification is the hand-reviewed inventory.** Keeping control-plane operations out of it rests on reviewing each route, including what a listed data-plane operation may write as a side effect, such as the user account a representative's `create_user` creates. Step 1a adds the registry and its fail-closed test for the whole API.
- **In v1, update includes delete.** A connection allowed to update can also use the two delete tools (vulnerabilities, task templates). Step 1a separates Delete.

### What would change this assessment

Giving the sidecar database access or a backend secret, letting it forward credentials other than MCP tokens, accepting MCP tokens on operations outside the inventory or with another audience, presenting them to any other resource, removing the backstop, or dropping the proxy isolation rules from the default configuration would reopen these questions and requires a new decision.
